# EASIFEM development conventions

Apply these rules in every EASIFEM repository. If the repository has its
own `AGENTS.md`, read it first; where it is more specific, it wins (except
for build permission, see "AGENTS.md conflicts").

## How to work with the user

1. **One task at a time.** Propose the single next task, mention any
   problem found, and ask how the user wants it done before editing. The
   user often has a specific approach in mind. Do not bundle unrelated
   changes into one step.
2. **Explain, then let the user choose.** For bugs and design questions,
   explain the issue and give options `(a)`, `(b)`, `(c)` with a
   recommendation (including performance where relevant). "Docs only" is
   a common valid choice. Wait for the choice.
3. **Review on request.** When the user says "I have made changes, review
   them", review the diff (use `/review`) without editing.
4. **Commit only when asked.** One commit per module or logical group,
   with a clear message. Never include `examples/CMakeLists.txt` (it is
   regenerated by `easifem run`).

## Reporting code locations

Whenever you mention code in a bug, finding, change or summary, name its
location as `FileName:MethodName`:

- Preferred: `FileName:MethodName`, using the file name and the procedure
  name as written in the source, for example
  `MeshField_Class@ConstructorMethods.F90:obj_Initiate2`. Name the specific
  procedure (`obj_Initiate2`), not the generic or binding (`Initiate`).
- Fallback: `FileName:LineNumber`, only when the code is outside any
  procedure (type definition, module-level declaration, `USE` line,
  `CMakeLists.txt`, TOML or other non-Fortran files).
- Use the bare file name. Add the path only if the name is ambiguous.
- If a procedure is long, quote the statement after the location.

A file name alone is not a location. In a list of changes, give one
`FileName:MethodName` per changed procedure.

## Golden rules: approval

1. **Edits, `${CLAUDE_PLUGIN_ROOT}/scripts/build.sh`, `${CLAUDE_PLUGIN_ROOT}/scripts/run-test.sh`, `easifem test` are
   allowed** without asking.
2. **`easifem install` is allowed without asking.** It writes to the
   shared install (`~/.easifem/easifem/install/<lib>`), which all other
   branches and the kernels link against. Never run `install` without
   `--no-download`.
3. **More than 10 files → ask first.** If a task will create, modify or
   delete more than 10 files in total (across all repositories), list the
   files and the reason before touching any, and wait for approval.
4. **Always ask before:** `easifem clean`, deleting files, `git commit`
   (unless the user asked for commits), `git push`, `git merge`,
   `git rebase`, `git reset --hard`, or deleting branches.
5. A plugin hook enforces rules 2 and 4 where it can. Do not work
   around it.

## Library layout and dependencies

| Library | Role | Depends on |
|---|---|---|
| base (easifemBase) | Core: data types (`BaseType`) + methods, multiple dispatch | external packages |
| classes (easifemClasses) | Core: object-oriented classes | base |
| elasticity, seepage, diffusion | Independent kernels | base, classes |

The kernels do not depend on each other.

## Build commands

Use only the easifem CLI (`~/go/bin/easifem`), through the plugin scripts
for compiling and running. Never run `cmake`, `ninja` or `make` directly.

The scripts wrap `easifem dev` and `easifem run`, print only error lines
and `ok`/`not ok` counts, and exit 1 on any compile, link, crash or
`not ok`. On failure they print the path of the full log.

| Purpose | Command |
|---|---|
| Compile (check a change compiles) | `${CLAUDE_PLUGIN_ROOT}/scripts/build.sh <lib>` |
| Install (needed before running examples) | `easifem install <lib> --no-download` |
| Run examples/tests | `${CLAUDE_PLUGIN_ROOT}/scripts/run-test.sh <File>.F90 [<File>.F90 ...]` |
| Run all examples in the examples dir | `cd <examples dir> && easifem test ./` |
| Clean (ask first) | `easifem clean <lib> [<lib> ...]` |

What the CLI does (from easifemGO):

- `dev`: CMake configure (Debug, shared) + build in the package build
  dir. No install. Exits non-zero only when a line contains `Error:`;
  linker failures (`ld:`, `collect2: error`, `FAILED:`,
  `ninja: build stopped`) can pass silently, so read the output.
- `install`: configure (package build type) + build + `cmake --install`
  into the shared install dir. **Always pass `--no-download`**: without
  it the CLI downloads the source into the package source dir.
  `dev` and `install` share the build dir; if the build types differ,
  switching between them triggers a full rebuild.
- Use `--verbose` in `build` and `install` if full compiler logs are desired.
- `clean`: deletes **both** the build dir and the install dir of each
  package. Afterwards dependants cannot link until it is reinstalled.

`<lib>` is one of `base`, `classes`, `elasticity`, `seepage`, `diffusion`.
Running examples needs a `runner.toml` in the same directory; see
`references/running-examples.md` before running anything.

### Workflow after a change

1. `${CLAUDE_PLUGIN_ROOT}/scripts/build.sh <lib>`; fix compile errors.
2. To run tests: `easifem install <lib> --no-download`, then
   `${CLAUDE_PLUGIN_ROOT}/scripts/run-test.sh <File>.F90`. Report `ok` / `not ok` counts per file.

### Major changes and downstream builds

A change is **major** when it does any of:

- changes a method interface (arguments, their types/kinds/intents,
  result, or the specific procedure name),
- adds a new field (component) to a class or type,
- adds a new method to a class or type.

Anything else (implementation-only edits inside submodules, docs) is
minor.

- Major change in **base** → install base, then
  `${CLAUDE_PLUGIN_ROOT}/scripts/build.sh classes`.
- Major change in **classes** → do not build kernels. Compile a kernel
  only when the user is working on it; mention that a previously built
  kernel may need recompiling next time.
- After an interface change, run the affected tests with
  `${CLAUDE_PLUGIN_ROOT}/scripts/run-test.sh`, which rebuilds from scratch; stale objects crash.

Always state whether a finished change is major or minor and which
downstream step (if any) is needed.

### Clean

Suggest `easifem clean <libs>` after build failures that look like stale
build state (`.mod`/`.smod` mismatches, "cannot open module file",
submodule/interface mismatch after a major change), or on request.

### AGENTS.md

A repository's `AGENTS.md` holds only repository facts (layout,
dependencies, paths). The rules in this plugin apply on top of it. If an
older `AGENTS.md` says to ask before every build, the rule above
(dev/run/install allowed, clean asks) wins.

## Code style (summary)

- Fortran 2018, free form, `.F90` for all new files (`.f90` is legacy).
- Module/submodule split: interfaces in
  `src/modules/<Module>/src/<Name>.F90`, implementations in
  `src/submodules/<Module>/src/<Name>@<Category>.F90` using
  `MODULE PROCEDURE`. Categories: `ConstructorMethods`, `GetMethods`,
  `SetMethods`, `IOMethods`, ...
- Naming of classes, methods and overloads: **follow
  `references/naming.md`** (PascalCase bindings, `obj_` prefix, numbered
  overloads — never type-suffixed).
- `IMPLICIT NONE` everywhere; modules `PRIVATE` by default with explicit
  `PUBLIC`; type components and bindings `PRIVATE` unless public API.
- Every `USE` has `ONLY`, **one imported item per line**; `USE` lines
  sorted alphabetically by module name.
- Kinds from `GlobalData`: `REAL(DFP)`, `INTEGER(I4B)`, `LOGICAL(LGT)`.
- Every dummy argument has `INTENT` and a `!!` comment; each binding has
  a one-line `!!` comment.
- Line length ≤ 78. Variables camelCase.
- GPL v3 header in library sources; never in example/test programs.
- classes debug rules (details in `references/templates.md`):
  - `[START]`/`[END]` messages in every procedure, inside
    `#ifdef DEBUG_VER`; `[END]` also before each early `RETURN`.
  - Error checks only in DEBUG mode (`e%RaiseError(...)` or
    `AssertError1/2/3`); no release-mode checks or fallbacks, and do not
    flag their absence in reviews.
  - `modName` is declared in each submodule, `myName` in each procedure,
    both inside `#ifdef DEBUG_VER`.
- base errors: `ErrorMsg`.
- HDF5 data layout: `group/<TypeName><Rank>/<name>`, e.g.
  `group/IntR0/n`, `group/RealR1/x`, `group/VectorFieldR0/u0`,
  `group/STVectorFieldR0/fext`, `group/MeshFieldR0/<var>`. Export a field
  with its own `Export` method.

## Documentation

Every public interface has a FORD docblock with an `Examples` program
(`references/docblock-style.md`). **Whenever a method changes, update its
docs in the same change** (see "Keeping docs in sync with code" there).
Do not list doc updates in reports; do report docs or tests left for
later.

## Linting and formatting

- `fortitude.toml` sets `fix = true`: **always run
  `fortitude check --no-fix <files>`** when checking; a plain
  `fortitude check` rewrites files. Never lint while changes are stashed.
- `fprettier` runs from a per-repository pre-commit hook. Never install
  hooks globally (`core.hooksPath`).

Much existing code predates these rules. Apply them to new and changed
code; change old code only as an explicit refactoring task (`/refactor`).
